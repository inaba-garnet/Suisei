# サーバーの技術選定

## Web フレームワーク
- axum を使う。tower-http のミドルウェアをそのまま使え、未実装エンドポイントを fallback でまとめて受けられるため。

## DB ライブラリ
- sqlx を使う。SQL をコンパイル時にスキーマと照合でき、PostgreSQL にも同じ API で移れるため。
- クエリは sqlx のマクロで書き、`cargo sqlx prepare` で作る `server/.sqlx/` をリポジトリに入れる。DB のない CI でも、SQL とスキーマを照合するため。
- 将来 PostgreSQL に移りやすいよう、クエリは DB 層のモジュールに閉じ込め、SQL は SQLite と PostgreSQL に共通する書き方に限る。
  - upsert は `ON CONFLICT`、挿入した行は `RETURNING` で取る。
  - 日時は ISO 8601 の文字列か UNIX 時刻で持ち、SQLite の日付関数に頼らない。
  - 並べ替えのキーはアプリで計算して列に保存し、DB 独自の照合順序に頼らない。
  - 全文検索は方式が違うので、一つのモジュールに隔離する。

## 画像処理
- `image` クレートを使う。純粋な Rust で、musl の静的バイナリにそのまま入るため。

## トランスコード
- ffmpeg を別のプロセスとして起動し、その出力をそのまま返す。FLAC、ALAC、WAV などを読めて MP3 と Opus に書き出せ、MP3 や Opus の実用的なエンコーダを静的バイナリに組み込まずに済むため。
- ffmpeg の場所は `SUISEI_FFMPEG`（既定は `ffmpeg`）で渡す。見つからなければ warn を残して元のファイルを返す。
- 本番の Docker イメージには ffmpeg を入れる。

## 形態素解析
- 読みの推定には lindera を使う。辞書を mmap か埋め込みのまま読むので起動が速く、NAS でもメモリが少なくて済むため。
- 辞書は IPADIC に、Mozc UT 辞書（`mozcdic-ut-jawiki`、`mozcdic-ut-personal-names`）の漢字を含む語を固有名詞として足したもの。IPADIC は人名や新しい作品名を読めず、Wikipedia の記事名から作られた UT 辞書が毎月更新されて補えるため。NEologd は更新が止まっていて、辞書も 700MB と大きい。
- UT 辞書の語には、長いほど小さいコストを付ける。同じコストだと短い語に分けたほうが安くなり、`富田美憂` を `富田` と `美憂` に分けて読み違えるため。
- 辞書は `server/dict/` のクレートの build.rs で取得して変換し、バイナリに埋め込む。版とハッシュは build.rs で固定する。一つのバイナリで配れるようにするため。別のクレートにするのは、CI のキャッシュに依存クレートとして残し、毎回作り直さないため。
- UT 辞書の jawiki は CC BY-SA なので、出典とライセンスを `server/dict/README.md` に書く。

## HTTP クライアント
- 外部の API（Spotify、docs/spotify.md）は `reqwest` で呼ぶ。TLS は rustls にし、暗号の実装に ring を使う。musl の静的バイナリに OpenSSL を持ち込まないため。reqwest の既定の aws-lc-rs は、ライセンスに OpenSSL を含み、ビルドも重い。
- 証明書は OS の証明書ストアで確かめる（`rustls-platform-verifier`）。同梱のルート証明書は、更新にバイナリの作り直しが要るため。Docker イメージには `ca-certificates` を入れる。
- ring などが使う `ISC` を、ライセンスの `accepted` に足した。MIT と同じ程度の許諾で、表示の義務も同じため。

## キャッシュ
- 作り直せるデータは、データの置き場所の下の `cache/` に、種類ごとのディレクトリを作って置く。音楽フォルダには書き込まない。

## DB のバックアップ
- サーバーが自分で DB を `VACUUM INTO` で写す。お気に入り、評価、プレイリスト、再生回数は DB にしかなく、音楽フォルダから作り直せないため。Docker の外に sqlite3 や cron を用意せずに済み、`VACUUM INTO` は読み取りのトランザクションの中で写すので、書き込み中でも整合した一つのファイルになる。
- 置き場所は `SUISEI_BACKUP_DIR`（既定はデータの置き場所の下の `backup/`）。書き終えるまでは `.tmp` の名前で書き、終わってから名前を変える。途中で止まったファイルを完全な写しと取り違えないため。
- 定期の写しは `suisei-<UTC の時刻>.db`（`suisei-20261005T120000Z.db` の形）。最新の写しの時刻から設定の間隔（既定は 1 日）が過ぎたら写し、設定の世代数（既定は 7）を残して古いものから消す。どちらかが `0` なら定期の写しを止め、残っている写しも消さない。外の仕組みで写す人が、置き場所の容量を使わずに済むようにするため。マイグレーションの前の写しは止めない。間隔をファイルの時刻から数えるので、再起動が続いても写しすぎず、休止の後は起きた時点で遅れを取り戻す。過ぎたかは 1 分おきに壁の時計で確かめる。単調時計は休止の間に進まないため。
- 起動時に未適用のマイグレーションがあれば、適用の前に `suisei-pre-migrate-<適用済みの版>-<時刻>.db` を写す。新しい版で DB を壊しても、直前の状態へ戻せるようにするため。直近の 3 つを残し、定期の世代とは別に数える。写せなければ起動をやめる。写しのないまま DB を書き換えないため。DB が新しいとき（マイグレーションの表がないとき）は写さない。
- 既定の置き場所は DB と同じボリュームなので、ディスクの故障には備えられない。別のディスクや外部へは、NAS のバックアップの仕組みで `backup/` を写す。
- 戻し方は README の「バックアップ」に書く。

## 応答の形式
- 応答のモデルは JSON だけで書き、XML は JSON から機械的に作る。スカラーは属性、オブジェクトと配列は子要素、`value` は本文にする。

## 設定
- 起動に要る設定は、起動引数と環境変数のどちらでも渡す（clap の `env`）。環境変数は `SUISEI_` で始める。
- 動かしながら変えたい設定は、DB の一行の表に持ち、Web クライアントの設定の画面から変える（`GET`、`PUT /api/settings`）。定期スキャンの間隔、DB のバックアップの間隔と世代数、`キャラクター(CV:声優)` を分けるか、Spotify の Client ID。NAS の compose を書き換えてコンテナを起動し直さずに済むため。
- 待ち受けのアドレス、置き場所のパス、利用者名とパスワード、`SUISEI_TRUST_FORWARDED_FOR` は環境変数に残す。起動の前に要るか、Web から変えられると認証の制限を外せてしまうため。
- 設定の画面に移した項目の環境変数は読まない。環境変数と DB の両方に値があると、どちらが効くかの規則が要るため。渡されていたら、起動時に warn で知らせる。
- 変えた設定は、再起動せずに効かせる。定期スキャンは新しい間隔で次の時刻を数え直し、タグの解釈は次のスキャンから使う。バックアップは次の確認（1 分おき）から新しい間隔と世代数を使う。
- 定期スキャンの間隔は 1 分以上、バックアップの間隔は 1 時間以上、世代数は 100 までにする。`0` はどれも止める意味で受け付ける。
- `SUISEI_DEV`（既定は false）で開発モードにする。検証用サーバーでは有効にし、Web クライアントが未完成の UI を出す（docs/web.md の「開発」）。Web はバイナリに埋め込んだ静的ファイルなので、ビルドし直さずに切り替えられるよう、サーバーの設定として持つ。

## Web クライアントのログイン
- `POST /api/login` で利用者名とパスワードを確かめ、セッションの Cookie を発行する。Web クライアントがパスワードをブラウザに保存しないため。
- セッションは DB の表に持ち、最後に使ってから 30 日で切れる。最終利用日時の更新は 1 時間に一度までにする。`stream` などのたびに DB へ書き込まないため。
- `GET /api/me` は Cookie を発行し直して期限を延ばす。Web クライアントは起動時にこれを呼ぶ。応答には開発モードかどうか（`dev`）も入れる。Web が起動時に一度で受け取れるため。
- Cookie は HttpOnly、SameSite=Strict にし、`X-Forwarded-Proto: https` のときは Secure も付ける。TLS はリバースプロキシが終端するため。偽装されても、影響は送り主自身の Cookie に限られる。
- `/api` の POST は `Content-Type: application/json` のときだけ受け付ける。SameSite と合わせて、別のサイトのフォームから送らせないため。
- Subsonic API は、`u`、`p`、`t`、`s`、`apiKey` のどれもないときに限り、Cookie のセッションで認証する。Cookie があって切れているか不正なら、エラー 40 を返す。Web クライアントがログイン画面に戻る判断に使うため。
- 期限の切れたセッションは、ログインのときにまとめて消す。

## 認証の総当たりの制限
- Subsonic API（パスワードの誤りと apiKey の誤り）と `POST /api/login` の失敗を、送り主の IP ごとにまとめて数える。どちらからでもパスワードを試せるため。利用者は一人なので利用者名で数えても全体と変わらず、全体で数えると本人のクライアントまで締め出せてしまう。
- 15 分の間に 10 回を超えて失敗したら、その IP からの認証を 15 分拒む。拒む間は正しいパスワードでも通さない。通すと、拒否中も総当たりを続けて当たりを知れるため。成功したらその IP の回数を消す。
- 拒むときは、Subsonic API ではエラー 40、`/api/login` では HTTP 429 を返す。HTTP 429 は Subsonic の仕様になく、クライアントが通信の失敗とみなして再送を繰り返すおそれがあるため。
- 引数の不足や非対応の方式、Cookie のセッションは数えない。前者は総当たりにならず、後者のトークンは推測できない長さの乱数のため。
- 時刻は壁の時計で測る。単調時計は休止やスリープの間に進まず、休止しがちな Sprite で拒否が明けなかったため。
- 回数はメモリに持つ。IP を変えながら送られてもメモリが際限なく増えないよう、記録は 1 万件までにし、溢れたら最後の失敗が最も古いものから消す。期限の切れた記録は 5 分おきにまとめて消す。IPv6 は一つの回線に割り当てられる /64 ごとに数える。
- 多くの IP から少しずつ試す攻撃は止められない。長いパスワードと、外から VPN 経由で入る構成で備える。
- 送り主の IP は接続元のアドレスを使う。`SUISEI_TRUST_FORWARDED_FOR` を付けたときだけ `X-Forwarded-For` の最後の要素を使う。プロキシのない構成でヘッダーを信じると、偽装で制限を外せてしまうため。

## Web クライアントの配信
- `web/.output/public`（Web のビルド結果）を `rust-embed` でバイナリに取り込み、`/rest` と `/api` 以外のパスで配る。サーバーを一つのファイルのまま置けるため。debug ビルドでは実行時にディスクから読むので、Web を作り直してもサーバーのビルドは要らない。
- ビルド結果がなくてもコンパイルは通す。サーバーだけの開発と CI に Node.js を要らなくするため。このとき `/` は仮の応答（`Suisei`）を返す。Amperfy はログインの前に `/` を GET し、400 以上なら接続を諦めるため。
- ファイルがなく拡張子もないパスには `index.html` を返す。画面の URL で直接開けるようにするため。拡張子のあるパスと `/api` の知らないパスは 404 を返し、warn で記録する。
- `_nuxt/` の下は 1 年の `immutable`、そのほかは `no-cache` にする。前者はファイル名に内容のハッシュが入り、後者はデプロイをすぐ反映したいため。
- 圧縮はしない。ビルド結果は 540KB ほどで、スマホの回線でも待ち時間が小さいため。

## ツールチェーン
- `server/rust-toolchain.toml` で Rust のバージョンを固定する。
- 検証用サーバーには musl の静的バイナリを送る。Sprite にツールチェーンもリポジトリの認証も要らないため。

## Docker イメージ
- 本番はリポジトリの直下の `Dockerfile` で作るイメージで動かす。Web をビルドしてサーバーに埋め込み、コンテナ一つで Web と API を配る。
- 土台は Debian の slim で、ffmpeg は Debian のパッケージを入れる。ffmpeg（GPL）のソースを Debian から入手でき、検証用サーバー（Debian の ffmpeg）と挙動がそろうため。
- データは `/data`（書き込み可のボリューム）、音楽フォルダは `/music`（読み取りだけでマウント）に置く。サーバーは音楽フォルダに書き込まないため。
- uid 1000 の利用者で動かす。NAS の権限に合わせるときは compose の `user` で変える。
- `SUISEI_DEV` は付けない。
- PR と main の CI はイメージがビルドできることだけ確かめる。`v0.1.0` のようなタグを push したときだけ、GHCR（`ghcr.io/inaba-garnet/suisei`）に載せる。タグは `0.1.0`、`0.1`、`latest` を付け、`0.1` を指せば同じ系列の修正だけを取り込める。
- イメージは x86_64 だけ作る。本番の NAS が x86_64 で、arm64 も作ると QEMU の上で Rust をビルドすることになり、CI が長くなりすぎるため。

## ライセンスの表示
- Suisei 自身は MIT。
- バイナリに入る Rust の依存のライセンスは `server/THIRD_PARTY_LICENSES.md` に置く。cargo-about で `Cargo.lock` から作り、CI で最新かを照合する。リポジトリに入れておけば、ソースを配る間は足りるため。
- ビルド用と開発用の依存はバイナリに入らないので載せない。読みの辞書のライセンスは `server/dict/README.md` に書く。
- イメージには、Suisei、依存、辞書のライセンスを `/usr/share/doc/suisei/` に入れる。
- タグごとに GitHub の Release を作り、イメージに入れた Debian のパッケージの一覧（名前と版）と、ffmpeg（GPL）の Debian のソースパッケージを添える。ほかの GPL のパッケージ（bash など土台のもの）は、一覧の版で Debian のアーカイブから入手できる。すべてのソースを添えると数百 MB になるため。

## 依存の照合
- ライセンスは、一覧を作る cargo-about の `accepted` で照らす。並べたもの以外のライセンスの依存が入ると一覧を作れず、CI が落ちる。同じ照合を二つの道具で持たないため、cargo-deny では照らさない。
- 脆弱性は cargo-deny の `advisories` で、毎日の定期実行で照らす。脆弱性の情報は変更と関係なく増え、PR の CI に入れると無関係な変更が落ちるため。公開リポジトリでは Actions の時間を数えないので、毎日にして気付くのを早める。
- 落とすのは、開発用を除く依存の脆弱性と、直接の依存の保守停止だけ。間接の依存の保守停止と取り下げられた版は警告に留める。直せない通知が並ぶと、直すべきものが埋もれるため。

## 未対応のエンドポイント
- 実装しない機能は、ポッドキャスト、共有、ジュークボックス、インターネットラジオ、チャット、動画、ブックマーク、ユーザー管理、`search`（v1）、`hls`。一人で NAS の音楽ファイルを聴く用途に要らないため。
- 実装しない機能の一覧を取る呼び出しは、空の一覧を返す。空なら画面のその欄が空になるだけで、知らないクライアントでも止まりにくいため。
- それ以外の操作は HTTP 501 を返す。ただし `deleteBookmark` は何もせず成功を返す。ブックマークを持たないので消した後の状態と一致し、失敗を返すと Symfonium が削除を再送し続けるため。
- 外部の情報源が要るもの（`getArtistInfo2`、`getAlbumInfo2`、`getSimilarSongs2` とその v1 版）は、空の情報を返す。外部の情報源を使っていないため。
- Subsonic と OpenSubsonic の仕様にない名前には HTTP 404 を返し、warn で記録する。Subsonic のエラー 70 は「求めたデータがない」の意味で、クライアントが曲の欠落のように表示するおそれがあるため。
