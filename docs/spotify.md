# Spotify 連携

設計判断とその理由だけを書く。最初の機能はお気に入りの取り込みで、ほかの機能（プレイリストの取り込みなど）は同じ接続と対応表の上に足す。

## 範囲
- Spotify の「お気に入りの曲」（Liked Songs）を読み、ローカルの同じ曲をお気に入りにする。向きは Spotify からローカルへの一方向に限る。
- 書き込みの権限（`user-library-modify`）は求めない。読むだけの機能に、Spotify のライブラリを書き換えられるトークンを持たせないため。逆向きの同期を足すときに、権限を足して接続し直してもらう。
- ローカルにない曲は取り込めない。音源を Spotify から得る手段はないので、対応しなかった曲は一覧で見せるだけにする。

## Spotify のアプリ
- 利用者が自分で Spotify のアプリを登録し、その Client ID を Web の設定の画面で入れる（docs/server.md の「設定」）。Suisei は各自が立てるサーバーなので、共通の Client ID を配れない。開発モードのアプリは利用者 5 人までだが、一人で使う前提なら足りる。
- 開発モードのアプリは、登録した人が Spotify Premium に入っている必要がある（2026 年 2 月の変更）。README の手順に書く。
- 認可は Authorization Code with PKCE で行い、Client Secret は持たない。秘密を設定に置かずに済むため。
- 未設定なら Spotify 連携の API を使えなくする。
- Client ID を変えたら接続を切る。接続は Client ID ごとに発行されるため。対応表とローカルのお気に入りは残す。
- 登録の手順は README に書く。
  1. Spotify for Developers のダッシュボードでアプリを作り、使う API に Web API を選ぶ。
  2. Redirect URI に `http://127.0.0.1:27533/callback` を登録する（「認可の戻り先」）。
  3. アプリの Client ID を設定の画面に入れる。
  4. Web の設定の画面で「Spotify に接続」を押し、Spotify で許可する。
  5. ブラウザが開けなかったページのアドレスバーの URL を、設定の画面に貼り付ける。

## 認可の戻り先
- 戻り先は `http://127.0.0.1:27533/callback` に固定し、認可の後にブラウザが開けなかったページの URL を、Web の設定の画面に貼り付けてもらう。サーバーはその URL からコードを取り出してトークンに換える。
- サーバーで直接コードを受けないのは、Spotify がリダイレクト URI に HTTPS か、ループバックの IP しか認めないため。NAS を LAN の HTTP だけで使う人でも、HTTPS の公開 URL を用意せずに連携できる。HTTPS の構成でも手順を一つにそろえる。
- `localhost` ではなく `127.0.0.1` にする。Spotify は `localhost` を Redirect URI として認めないため。
- ポートは 27533 にする。番号のない 80 番だと、利用者の PC で動いている別のサーバーのページが開くことがあるため。よく使われる番号（8080、8888 など）と、OS が一時的に割り当てる範囲（32768 以上）を避けた。
- 戻り先を設定にしない。決まった値なら、利用者は README の値をそのまま登録すればよく、設定と Spotify 側の登録が食い違わないため。
- 貼り付けた URL の `state` を、認可を始めたときの値と照らす。別の認可で得た URL を取り違えて貼っても、つながないため。
- `state` と PKCE の verifier はメモリに持ち、10 分で捨て、一度使ったら消す。再起動で消えても、認可をやり直せば済むため。

## トークン
- リフレッシュトークンを DB の一行の表に持つ。アクセストークンは 1 時間で切れるのでメモリにだけ持ち、切れたらリフレッシュトークンで取り直す。
- リフレッシュで新しいリフレッシュトークンが返れば、置き換えて保存する。PKCE のリフレッシュトークンは使うたびに替わることがあるため。
- リフレッシュが `invalid_grant` で失敗したら、接続が切れたとして表を消し、Web で接続し直すよう伝える。
- DB のバックアップにもトークンが入る。権限を読み取りに限るので、漏れても Spotify のライブラリは書き換えられない。
- 接続を切るときは表の行を消す。Spotify 側のアプリの許可は、利用者が Spotify のアカウント設定で外す（API で取り消す手段がない）。

## 取り込み
- `GET /v1/me/tracks` を 50 件ずつ全件読む。前回からの差分だけを読む手段はなく、追加日時で打ち切ると Spotify 側で外した曲を拾えないため。数千曲なら百回程度の要求で済む。
- 読んだ曲は、Spotify の ID、ISRC、曲名、アーティスト（一人ずつ）、アルバム名、ディスク番号、トラック番号、長さ、お気に入りにした日時を、対応表（`spotify_track`）に保存する。スキャンで曲が増えたときに、Spotify を呼ばずに対応を付け直すため。
- 今回の一覧にない行は対応表から消す。
- `Accept-Language: ja` を付けて読む。付けないと、日本のアーティストの名前がローマ字（`Yui Sakakibara` など）で返り、タグの表記（`榊原ゆい`）と合わないため。
- 対応したローカルの曲がお気に入りでなければ、Spotify でお気に入りにした日時でお気に入りにする。すでにお気に入りなら、日時は古いほうにする。マージのときの規則（docs/schema.md の「お気に入りと評価」）とそろえるため。
- お気に入りにするのは、対応を付けたときだけにする。対応済みの曲は、取り込みのたびにお気に入りにし直さない。ローカルで外したお気に入りを、毎時の取り込みで戻さないため。
- Spotify で外した曲のお気に入りを、ローカルで外すことは範囲に入れない。ローカルで付けたお気に入りと区別せずに外すと、利用者が手で付けたものを失うため。
- 取り込みは Web の設定の画面から手動でも始められる。
- スキャンが終わるたびに、Spotify を呼ばずに、対応表の未対応の行に対応を付け直す。スキャンで増えた曲にすぐ対応を付けるため。
- 接続していて、前の取り込みを始めてから 60 分たっていれば、付け直す前に Spotify から読み直す。取り込みのための間隔の設定を別に持たずに済み、スキャンの間隔を短くしても Spotify の API を呼びすぎないため。
- 定期のスキャンを止めている（間隔が `0`）ときは、スキャンの後に Spotify から読まない。
- 前の取り込みを始めた日時は DB に持つ。再起動のたびに Spotify を呼ばないため。
- 429 が返れば `Retry-After` の秒数だけ待って続ける。2 分より長く待てと言われたら、その回は諦めて次のスキャンの後にやり直す。
- 取り込みは一度に一つだけ走らせる。

## 曲の対応
- 次の順で探し、最初に一曲に決まったものを採る。候補が二曲以上の段は飛ばして次の段で探す。
  1. ISRC が一致する曲。
  2. `match_key` が一致する曲。Spotify の曲名、アーティスト、アルバム、ディスク番号、トラック番号から、ローカルと同じ規則で鍵を作る。
  3. 曲名とアーティストが一致し、長さの差が 3 秒以内の曲。アルバム、ディスク番号、トラック番号は見ない。曲名とアーティストは `match_key` と同じ規則（`キャラクター(CV:声優)` の分け方を含む）で正規化して比べる。長さはローカルの配信に使うファイルの長さ。
- ISRC が一致しなくても、2 と 3 で探す。ローカルのファイルに ISRC がないことが多く、同じ録音でも盤によって ISRC が違うことがあるため。
- `match_key` はアルバム、ディスク番号、トラック番号を含むので、2 で対応するのはローカルと同じ盤の曲に限られる。シングルとアルバムやベスト盤のように盤が違う曲は、3 で拾う。
- ISRC が同じ曲がアルバムとベスト盤の両方にあれば、1 では決まらず、2 で盤まで一致する曲を選ぶ。
- どの段でも一曲に決まらなければ対応させない。同じ曲名のライブ版やリマスター版を取り違えるより、未対応で見せるほうがよいため。
- ISRC を使うため、タグの `ISRC`（ID3v2 の `TSRC`、Vorbis の `ISRC`、MP4 の `----:com.apple.iTunes:ISRC`）を読む。保存するタグの版を上げるので、次のスキャンで全ファイルを一度読み直す。
- ISRC は列に持たず、照合のときに保存した生のタグから読む。スキャンの書き込みを変えずに済み、照合は 1 時間に一度ほどなので読む手間は小さいため。
- ISRC は英数字だけを残して大文字にそろえて比べる。`JP-XX0-15-00001` のように区切って書かれたタグがあるため。
- 対応の結果は、対応表に曲の ID と方式（`isrc`、`match_key`、`fuzzy`、`manual`、`ignored`）で持つ。
- 手動の対応は Web から付ける。自動の対応で上書きしない。
- 手動で対応を外した曲は `ignored` にし、自動の対応も付けない。誤った自動の対応を外しても、次の取り込みで同じ曲に付け直さないため。
- 曲がマージで消えるときは、対応を残る側の ID へ付け替える。ファイルが消えて曲が消えたら、対応を外して未対応に戻す。

## API
- Subsonic API ではなく `/api/spotify` に置き、セッションの Cookie で認証する。Subsonic に Spotify 連携の仕様はなく、使うのは Web クライアントだけのため。
  - `GET /api/spotify`: 設定の有無、登録する Redirect URI、接続の状態、取り込み中か、最後の取り込みの日時と結果、件数（全件、対応済み）。未設定なら `configured: false` と Redirect URI だけを返す。アプリを登録する前に Redirect URI を見せるため。ほかの API は 404 を返す。
  - `POST /api/spotify/authorize`: 認可の URL を返す。
  - `POST /api/spotify/callback`: 貼り付けた URL を受け、コードをトークンに換える。
  - `DELETE /api/spotify`: 接続を切る。対応表は残す。
  - `POST /api/spotify/sync`: 取り込みを始める。終わるのを待たずに返し、状態は `GET /api/spotify` で見る。
  - `GET /api/spotify/tracks`: 対応表の一覧。`matched=false` で未対応、`matched=true` で対応済みに絞る。
  - `PUT /api/spotify/tracks/{spotifyId}`: 手動で対応を付ける（`{"trackId": "tr-..."}`）、外す（`{"trackId": null}`）。付けた曲はお気に入りにする。
- 書き込む要求は `Content-Type: application/json` のときだけ受け付ける。ログインの API と同じく、別のサイトのフォームから送らせないため。

## HTTP クライアント
- docs/server.md の「HTTP クライアント」。サーバーは `accounts.spotify.com` と `api.spotify.com` に外向きにつなぐ。

## Web クライアント
- 設定の画面に「Spotify」の項目を置き、接続、取り込み、最後の結果を出す。
- 未対応の曲を一覧で見せ、ローカルの曲を検索して手動で対応を付けられるようにする。
