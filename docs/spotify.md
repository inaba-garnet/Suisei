# Spotify 連携

設計判断とその理由だけを書く。最初の機能はお気に入りの取り込みで、ほかの機能（プレイリストの取り込みなど）は同じ接続と対応表の上に足す。

## 範囲
- Spotify の「お気に入りの曲」（Liked Songs）を読み、ローカルの同じ曲をお気に入りにする。向きは Spotify からローカルへの一方向に限る。
- 書き込みの権限（`user-library-modify`）は求めない。読むだけの機能に、Spotify のライブラリを書き換えられるトークンを持たせないため。逆向きの同期を足すときに、権限を足して接続し直してもらう。
- ローカルにない曲は取り込めない。音源を Spotify から得る手段はないので、対応しなかった曲は一覧で見せるだけにする。

## Spotify のアプリ
- 利用者が自分で Spotify のアプリを登録し、その Client ID を `SUISEI_SPOTIFY_CLIENT_ID` で渡す。Suisei は各自が立てるサーバーなので、共通の Client ID を配れない。開発モードのアプリは利用者 5 人までだが、一人で使う前提なら足りる。
- 開発モードのアプリは、登録した人が Spotify Premium に入っている必要がある（2026 年 2 月の変更）。README の手順に書く。
- 認可は Authorization Code with PKCE で行い、Client Secret は持たない。秘密を設定に置かずに済むため。
- 未設定なら Spotify 連携の API と画面を出さない。

## 認可の戻り先
- Spotify はリダイレクト URI に HTTPS か、ループバックの IP（`http://127.0.0.1:<port>`）しか認めない。LAN の `http://192.168.x.x` には戻せない。
- 戻り先は `SUISEI_SPOTIFY_REDIRECT_URI` で渡す。HTTPS の公開 URL があれば `https://<host>/api/spotify/callback` を登録してもらい、サーバーが直接コードを受ける。
- HTTPS の URL がない構成では、`http://127.0.0.1/callback` のような届かない URI を登録してもらう。認可の後にブラウザが開けなかった URL を、Web クライアントに貼り付けてもらってコードを取り出す。NAS を LAN の HTTP だけで使う人でも連携できるようにするため。
- `/api/spotify/callback` の GET はセッションの Cookie を見ずに、`state` で確かめる。Spotify から戻る遷移は別サイトからの遷移なので、SameSite=Strict の Cookie が付かないため。
- `state` と PKCE の verifier はメモリに持ち、10 分で捨て、一度使ったら消す。再起動で消えても、認可をやり直せば済むため。

## トークン
- リフレッシュトークンを DB の一行の表に持つ。アクセストークンは 1 時間で切れるのでメモリにだけ持ち、切れたらリフレッシュトークンで取り直す。
- リフレッシュで新しいリフレッシュトークンが返れば、置き換えて保存する。PKCE のリフレッシュトークンは使うたびに替わることがあるため。
- リフレッシュが `invalid_grant` で失敗したら、接続が切れたとして表を消し、Web で接続し直すよう伝える。
- DB のバックアップにもトークンが入る。権限を読み取りに限るので、漏れても Spotify のライブラリは書き換えられない。
- 接続を切るときは表の行を消す。Spotify 側のアプリの許可は、利用者が Spotify のアカウント設定で外す（API で取り消す手段がない）。

## 取り込み
- `GET /v1/me/tracks` を 50 件ずつ全件読む。前回からの差分だけを読む手段はなく、追加日時で打ち切ると Spotify 側で外した曲を拾えないため。数千曲なら百回程度の要求で済む。
- 読んだ曲は、Spotify の ID、ISRC、曲名、アーティスト（一人ずつ）、アルバム名、ディスク番号、トラック番号、長さ、お気に入りにした日時を、対応表（`spotify_track`）に保存する。スキャンで曲が増えたときに、Spotify を呼ばずに対応を付け直すため。
- 今回の一覧にない行は対応表から消す。
- 対応したローカルの曲がお気に入りでなければ、Spotify でお気に入りにした日時でお気に入りにする。すでにお気に入りなら、日時は古いほうにする。マージのときの規則（docs/schema.md の「お気に入りと評価」）とそろえるため。
- Spotify で外した曲も、ローカルのお気に入りは外さない。ローカルで付けたお気に入りと区別せずに消すと、利用者が手で付けたものを失うため。外すことを選べるようにするのは、要望が出てから考える。
- 取り込みは Web の設定の画面から手動で始める。定期実行は `SUISEI_SPOTIFY_SYNC_INTERVAL`（既定は `0`、止める）で選べる。間隔の数え方はスキャンと同じく、前の取り込みが終わってから数える。
- スキャンの後に、対応のない行だけを付け直す。Spotify は呼ばない。
- 429 が返れば `Retry-After` の秒数だけ待って続ける。取り込みは一度に一つだけ走らせる。

## 曲の対応
- 次の順で探し、最初に一曲に決まったものを採る。
  1. ISRC が一致する曲。
  2. `match_key` が一致する曲。Spotify の曲名、アーティスト、アルバム、ディスク番号、トラック番号から、ローカルと同じ規則で鍵を作る。
  3. 曲名と一人目のアーティストが一致し、長さの差が 3 秒以内の曲。曲名とアーティストは検索の照らし（docs/schema.md の「検索」）と同じ正規化で比べる。
- 候補が二曲以上なら対応させない。同じ曲名のライブ版やリマスター版を取り違えるより、未対応で見せるほうがよいため。
- ISRC を使うため、タグの `ISRC`（ID3v2 の `TSRC`、Vorbis の `ISRC`、MP4 の `----:com.apple.iTunes:ISRC`）を読む。保存するタグの版を上げるので、次のスキャンで全ファイルを一度読み直す。
- 対応の結果は、対応表に曲の ID と方式（`isrc`、`match_key`、`fuzzy`、`manual`）で持つ。
- 手動の対応は Web から付ける。自動の対応で上書きしない。
- 曲がマージで消えるときは、対応を残る側の ID へ付け替える。ファイルが消えて曲が消えたら、対応を外して未対応に戻す。

## API
- Subsonic API ではなく `/api/spotify` に置き、セッションの Cookie で認証する。Subsonic に Spotify 連携の仕様はなく、使うのは Web クライアントだけのため。
  - `GET /api/spotify`: 設定の有無、接続の状態、最後の取り込みの日時と結果、件数（全件、対応、未対応）。
  - `POST /api/spotify/authorize`: 認可の URL を返す。
  - `GET /api/spotify/callback`: Spotify から戻る先。コードをトークンに換え、Web の設定の画面へ移す。
  - `POST /api/spotify/callback`: 貼り付けた URL を受ける。
  - `DELETE /api/spotify`: 接続を切る。対応表は残す。
  - `POST /api/spotify/sync`: 取り込みを始める。終わるのを待たずに返し、状態は `GET /api/spotify` で見る。
  - `GET /api/spotify/tracks?matched=false`: 未対応の曲の一覧。
  - `PUT /api/spotify/tracks/{spotifyId}`: 手動で対応を付ける、外す。

## HTTP クライアント
- `reqwest` を rustls と同梱のルート証明書（`webpki-roots`）で使う。musl の静的バイナリに OpenSSL を持ち込まず、Docker イメージに CA 証明書を足さずに済むため。
- サーバーは `accounts.spotify.com` と `api.spotify.com` に外向きにつなぐ。

## Web クライアント
- 設定の画面に「Spotify」の項目を置き、接続、取り込み、最後の結果を出す。
- 未対応の曲を一覧で見せ、ローカルの曲を検索して手動で対応を付けられるようにする。
