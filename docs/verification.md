# 検証の方針

## 検証用サーバー
- Fly.io の Sprites で動かす。休止中は計算資源の料金がかからず、リクエストで自動的に起き、ディスク上の SQLite が公式に保証されているため。
- Claude は環境変数 `SPRITES_TOKEN` で Sprites の API を直接操作し、デプロイとログ確認を自分で行う。
- URL は公開にし、Subsonic の認証で守る。Symfonium は Fly.io の組織認証を通れないため。
- Sprite は Docker ではなく素の Linux で動く。本番用の Docker イメージは CI でビルドできることだけ確かめる。

## 動作確認
- 動作確認の基準クライアントは Symfonium。
- Symfonium が実際に送るリクエストを記録し、テストで再生する。
- タグの読み取りは、数 KB の無音の音声にタグを書いたファイルで確かめる。ファイルはリポジトリに入れ、作るスクリプト（`server/tests/fixtures/tags/generate.py`）も置く。
- テスト用のタグは mutagen で書く。読み取りに使う lofty とは別のライブラリにして、読み違いを書き込み側で打ち消さないため。
- 応答の妥当性は Navidrome（`demo.navidrome.org`）の応答と構造、必須項目を比べて確かめる。取得した応答はファイルに保存して使う。

## 実装予定のエンドポイント（仮の措置）
- 実装を予定しているエンドポイントは、実装するまで HTTP 200 と Subsonic のエラー（code 0）を返し、呼ばれたことを warn で記録する。HTTP のエラーではクライアントの同期が止まるおそれがあるため。
- 予定のないエンドポイントの応答は docs/server.md の「未対応のエンドポイント」に従う。
- `getAlbumList2` の `highest` と `starred` は、評価とお気に入りを持つまで空の一覧を返す。エラーにするとクライアントのホーム画面が止まるおそれがあるが、空の一覧ならその欄が空になるだけで済むため。
